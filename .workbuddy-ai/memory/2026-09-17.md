## 关键实测：batch 不是越大越好（4090 48G）

用户提出"显存太低，拉大 batch"。实测后结论相反 —— **在这张卡上 batch 越大吞吐越低**：
超过 ~40G 后呈超线性变慢（显存带宽 / 分配器压力），所以"占满显存"是错的优化目标。

| arm | batch | 显存 | s/step | samples/s |
|---|---|---|---|---|
| latent-S | **64** | 23.8G | 0.485 | **132.0** |
| latent-S | 112 | 41.0G | 0.895 | 125.1 |
| latent-XS | **96** | 12.0G | 0.293 | **327.7** |
| latent-XS | 320 | 39.5G | 1.526 | 209.7 |
| pixel-S | 24 | 35.1G | 0.857 | 28.0 |
| pixel-S | **28** | 40.8G | 0.947 | **29.6** |
| pixel-XS | **32** | 15.7G | 0.510 | **62.7** |
| pixel-XS | 64 | 31.2G | 1.143 | 56.0 |

只有 pixel-S 24→28 略微划算。结论：**按吞吐选 batch，不要按显存占用选**。
（数据：experiments/diffusion/bench_batch*.log，脚本 scripts/server/bench_batch3.sh）

补充诊断：
- pixel 曾被怀疑 dataloader 瓶颈（GPU 0% + 4 workers 满载），但 w16 只快 ~9%，不是主因
- AMP/bf16 确认生效；实际 ~25-30 TFLOPS ≈ 30% MFU，小 DiT 未 compile 属正常范围
- 真正能提速的是 torch.compile / kernel fusion，不是 batch（待办，未做）

1. **只有 pixel 的回归臂打赢了 bicubic。** 所有 latent 臂、所有 flow 臂都不如什么都不做。
2. **latent_reg 比自己的零初始化还低 0.47 dB** —— 训练不但没帮忙，还帮了倒忙。
3. 所以之前说的"latent 比 pixel 差 2.6 dB"是低估了严重程度：真实情况是 latent 回归
   **完全没学起来**。
4. lr 不是原因：3e-5 重跑的 VAL 曲线（1000:30.63 → 2000:28.53 → 3000:29.01）
   与原版（1000:30.47 → 2000:29.17）**一模一样**。LR 假设已否证。

**已排查的无关因素：**
- 缓存 latent 用的是 `sample=False`（确定性），不是采样噪声
- reg 目标 `z0_hat = zc + model(zc, t0)`，loss 对 z0（真 HR latent），路径正确
- latent 和 pixel 的 `--reg-loss` 默认都是 l1，一致
- `--sample-hr` 默认 0

**新假设（正在验证，`diag_latent_reg_alpha.py`）：**
把模型输出缩放 α ∈ {0,.25,.5,.75,1,1.25}，即 `z = zc + α·model(zc,t)`。
- 若某个 0<α<1 同时优于 α=0 和 α=1 → 模型学到了**方向对但幅度过大**的残差，
  根因是「latent 空间 L1 最优 ≠ 像素空间 PSNR 最优」，修法是像素域 loss 或调 scale
- 若从 α=0 起单调下降 → 模型确实什么都没学到
α=0 那一档同时交叉验证 VAE 往返地板 31.5971。

## 23:30 U-Net 分支 + 解码缓存（大进展）

**为什么换 U-Net（数据支撑，不是拍脑袋）**
重算 DiT-S 的 FLOPs：HR128 → n=4096 tokens，**attention 的 n² 项占 64%**
（每样本每层 25.8/40.3 GFLOP）。整步 40.6 TFLOP / 0.40s = **101 TFLOPS = 4090 峰值的 61%**
→ 确实是算力瓶颈，拉大 batch 没用（用户的判断是对的）。
但存算比已经 **1962 FLOP/byte**，远超 4090 的 ridge point（165）→ **提高存算比没收益**。
真正的杠杆是：64% 的算力花在全分辨率 n² attention 上，对 SR 是浪费。

**U-Net 实现（`diffusion/unet.py`）**
- `build_unet(size, ...)`，接口与 DiT 完全一致（`forward(x,t)`，x=(B,C,H,W)，t∈[0,1000]）
- base=64, mult=(1,2,4,4), num_res=2, attn 只在 level 2/3 → **18.67M 参数**
- ResBlock 第二个 conv 零初始化（DDPM 做法）→ 整个网络初始为恒等，reg 臂起点正好是 bicubic
- **native-LR**：`in_stride=2, out_scale=2` —— stem 一个 stride-2 卷积把图降到 LR 尺度，
  整个编码器/解码器都在 LR 尺度跑，skip 全部落在相同分辨率的层上，最后 pixel-shuffle 抬回 HR。
  最高分辨率上只剩一个 stem 卷积和一个 shuffle 卷积。省 ~29% FLOPs、**显存降 4.5 倍**。
  ⚠️ **只对 reg 有效**：flow 的 ODE 状态在 HR 带白噪声，下采样会混叠掉速度场必须重建的信息。
- `model.align` = in_stride × 2^(levels-1) × out_scale = 32，eval 必须按它对齐 tile

**实测（4090 48G，HR128，batch 390）**
| 模型 | 参数 | 显存 | s/step | samples/s |
|---|---|---|---|---|
| DiT-S | 34.0M | 20.7 GB | 0.40 | 70 |
| U-Net (native-LR) | 18.7M | 21.7 GB | 0.415 | **940** |
→ **13× 吞吐**。batch 704 时 38.4 GB / 1634 samples/s（但 704 > 训练集 390，需要放回采样）

**2500 步试跑（17 分钟）的 VAL**
```
VAL  500: 30.537 | 1000: 31.472 | 1500: 31.837 | 2000: 32.069 | 2500: 32.217
```
DiT pixel_reg 要到 VAL 3000~4000（约 50 分钟）才到 32.2 → **U-Net 墙钟快 ~3 倍**，
但样本效率更低（2500×390=97.5 万样本 vs DiT 3000×28=8.4 万）。4 对官方评估 32.91。

**踩的坑**
1. `build_unet(base=0)`：train_pixel 的 `--base 0` 表示"用 preset"，但 `setdefault` 不会替换
   已存在的 0 → `GroupNorm(0,0)` 除零。改成 `if not kw.get("base")`。
2. **eval 的 tile 对齐**：RealSR 的 HR 尺寸不是 32 的整数倍（1000%32=8），
   `_tile_windows` 把最后一块 clamp 到 H → U-Net 内部分辨率非对齐 → skip concat 尺寸不匹配。
   修法：把图 pad 到 align 的整数倍再跑，最后裁回来（latent 路径早就有这个处理）。
3. **batch > 数据集大小**：训练集只有 390 对，batch 704 + drop_last → 一个 epoch 凑不出
   一个 batch → StopIteration。加放回采样 + persistent_workers。
4. eval_official 原来没有 autocast（仓库里唯一一个），已加 `--bf16`（默认关，VAE 保持 fp32）。

**解码缓存（`diffusion/decoded.py` + `scripts/server/precache_hr.py`）**
4562 张图 / 31.23 GB / **21 秒**解码完（16 进程），落盘 `data/decoded/*.u8` + `manifest.json`。
`DecodedStore` 按**文件路径**索引，任何 dataset 都能直接用：
- `RealSRCropDataset` 10.95 ms/item（406/406 命中）→ 12 worker ≈ 1000 items/s ✅
- `BSRGANDataset` **153 ms/item**（3550/3550 命中）→ 12 worker 只有 84 items/s ❌

⚠️ **预训练的真正瓶颈是 BSRGAN 退化本身，不是解码**（估主要是 JPEG 编解码往返）。
batch 390 @0.42s 需要 929 samples/s，差 11 倍。四条路：A 预生成 K 版退化落盘、
B 砍掉/降低 JPEG 概率、C 用小 batch、D 加 worker（20 个也只有 140/s，无效）。

## 23:55 dataloader 线程爆炸（重要基建坑）+ 5 尺寸 sweep 计划

**根因：OpenMP 线程爆炸，不是算法慢**
`BSRGANDataset` 153 ms/item 里几乎全是线程调度开销。每个 DataLoader worker 起 24 个
OMP 线程 → 12 worker = ~288 个自旋线程抢 24 个核。这些是 128×128 的小卷积，本就该单线程：

| 操作（128×128） | 1 线程 | 24 线程 |
|---|---|---|
| `_blur` | **3.28 ms** | 33.03 ms |
| `_resize` | 0.26 ms | 4.34 ms |
| **完整退化** | **10.59 ms** | 153 ms |

**修法**：`train_pixel.py` 加 `_worker_init` → `torch.set_num_threads(1)`，传给 DataLoader
的 `worker_init_fn`。**loader 吞吐 84 → 258 samples/s。**
（不要用全局 `OMP_NUM_THREADS=1`，那会把主进程也算 SSIM 的 CPU 性能一起砍掉。）

**当前吞吐基线（12 worker）**
- BSRGAN 预训练数据：258 samples/s（退化是瓶颈）
- RealSR 微调数据：~1100 samples/s（解码瓶颈已由 `data/decoded` 消除）
